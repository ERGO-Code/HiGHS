Production step：五个有序操作

入口及四次 Backend 调用保持源码顺序。橙色卡片标出恰好两次 SpMV；A * next_primal 不在每个生产步中，它只在边界准备 candidate products 时发生。

  1. enqueueHalpernPdhgStep

    Host 控制器校验 14 个句柄、正步长、迭代计数与 scalar offset，并构造 primal step、dual step、anchor weight。

    CPU lane 同步调用 serial Backend；任一 api::Error 立即返回。
    CUDA lane 向 Backend stream 排队；录制时同样的调用成为 CUDA graph 节点。

  2. fusedProjectedPrimalUpdateAndReflect

    从 current_primal 与 current_aty 计算投影后的 primal_candidate，并产生 reflected_primal = 2*candidate-current。

    CPU lane · column loop serial for col：梯度更新、lower/upper clamp、反射与 finite check。
    CUDA lane · custom kernel projectedPrimalKernel<true>，column-sized grid-stride launch。

  3. multiplyAndProjectedDualUpdateAndReflect

    组合操作先计算 A * reflected_primal → reflected_ax，随后以 row bounds 更新、投影并反射 dual；forward product 不是一个额外的顶层算法调用。

    CPU lane · sparse loop + row loop multiplySparse(matrix, reflected_primal)，再执行 projected dual / reflection loop。
    CUDA lane · vendor + custom executeSpmv → cusparseSpMV，然后 projectedDualKernel<true>。
    SpMV 1/2 · A * reflected_primal

  4. fusedVectorBlend

    用 1/(next_iteration+1) 同时混合 primal/dual anchor 与 reflected vectors，写入 next_primal、next_dual。

    CPU lane · two serial loops 分别遍历 columns 与 rows，检查 weight 和输出有限性。
    CUDA lane · paired kernel 单次 vectorPairBlendKernel 覆盖 max(rows, cols)。

  5. multiplyTranspose，然后 commit state

    计算 A^T * next_dual → current_aty；成功后 swap current/next 指针并增加 iteration。这里没有 A * next_primal。

    CPU lane · transpose sparse loop multiplySparse(transpose, next_dual)；Host 完成 pointer swaps。
    CUDA lane · vendor SpMV executeSpmv → cusparseSpMV；排队成功后 Host 完成 pointer swaps。
    SpMV 2/2 · A^T * next_dual

顺序证据： algorithm/halpern_pdhg_step.cc · backend/cpu/cpu_backend.cc · backend/cuda/cuda_backend.cu

CUDA graph：1 direct + 39 recorded steps

在 40-step cadence 中，RecordedIterationBlock 捕获 39 个 production steps。每步 3 个 scalars，共 39 × 3 = 117 doubles = 936 bytes；replay 前上传参数，随后调用 cudaGraphLaunch。

Replay scheduling：The initial step and the first post-restart step execute directly. Short tails with fewer than 39 remaining steps execute directly.

Time-limit granularity：Host checks the time limit before submitting replay and after it completes; a submitted 39-step block cannot be interrupted by host time-limit checks.

Graph 保留资源的 weak lifetime dependencies，而不是拥有 problem/vector/workspace。捕获、实例化或 replay 的失败保持为 api::Error。

HiPDLP 例子：projectedPrimalKernel<true> 用 256 threads，blocks 为 min(ceil(num_cols / 256), 65535)，每个线程处理一个 column 起点并按整个 grid 的 stride 前进。

查看 cuda_kernels.cu

问题 1：一个线程如何覆盖不止一个 column？

展开参考答案

结论：每个线程处理一个起始索引，并按整个 grid 的 stride 继续前进。

代码证据：index += blockDim.x * gridDim.x。

Review 推理：静态代码能证明覆盖方式；实际吞吐和 occupancy 仍需 profiler。

问题 2：blocks 上限 65535 是否把可处理的向量长度也限制为 65535 × 256？

展开参考答案

结论：不会；上限只限制并发起点数量，grid-stride loop 继续覆盖更大的 N。

代码证据：blockCount() cap blocks，但 kernel 的 for (...; index < size; index += stride) 不 cap size。

Review 推理：要同时审查循环和索引类型；只看 launch geometry 会错误地推断覆盖缺口。

问题 3：projection 分支和 atomicExch(error_flag, 1) 分别影响什么？

展开参考答案

结论：上下界 clamp 可能造成 warp divergence；atomic 只把 non-finite 失败汇总为单向错误标志。

代码证据：if (value < lower[index])、if (value > upper[index]) 与 recordNonFinite()。

Review 推理：正确性可由分支和幂等标志判断；分支代价必须结合 bound 分布和 profiler 观察。

Checklist：

  • 为每个 kernel 写出 global index、stride 与边界条件。
  • 确认索引乘法不会在最大支持维度溢出。
  • 区分覆盖正确性、分支正确性与 occupancy 证据。

问题 1：VectorHandle 为什么不暴露 double*？

展开参考答案

结论：opaque handle 把驻留位置和资源类型封装在 backend 内，阻止算法层直接解引用或跨 backend 混用。

代码证据：Handle<Tag> 私有持有 std::unique_ptr<Resource>，只有 CPU/CUDA backend 是 friend。

Review 推理：类型封装能证明访问边界；owner、尺寸与 alias 仍必须由具体 backend 在每次操作中校验。

问题 2：为什么小型 check packet 仍使用 pinned memory？

展开参考答案

结论：pinned Host buffer 支持可靠的异步 D2H staging，并可在多次 cadence boundary 复用。

代码证据：PinnedCheckPacket::allocate() 调用 cudaMallocHost(..., sizeof(CheckPacket))。

Review 推理：复用和异步语义由代码可见；pinning 是否值得其固定成本需用边界频率与 timeline 衡量。

问题 3：连续 vector access 与 CSR SpMV 的访存证据为何不能混为一谈？

展开参考答案

结论：vector kernel 可按连续 index 获得 coalescing，而 CSR 的 index/value 访问受矩阵结构和 vendor kernel 控制。

代码证据：custom kernel 直接访问 current[index]；SpMV 通过 CSR descriptor 进入 cusparseSpMV。

Review 推理：源码可分类访问模式，但 cache hit、transaction 和有效带宽必须由 Nsight Compute 证明。

代码证据：CudaCommandBufferResource 保存 std::weak_ptr<int> dependencies，replay() 先调用 dependenciesAlive()。

Review 推理：Graph object 的生命周期不等于被捕获资源的生命周期；重放前的显式 guard 防止 use-after-free。

综合题 1：追踪 primal_candidate：从分配、kernel 写入、resident check、download 一直到 postsolve。

展开参考答案

结论：它是 backend-owned column vector：setup 创建，primal kernel 写入，边界检查在 Device 上读取，必要时下载到 HostIterate::primal，最后由 postsolve 恢复原模型语义。

代码证据：createIterationVectors() 创建它；fusedProjectedPrimalUpdateAndReflect(..., *state.primal_candidate, ...) 写入；check_input.primal = state.primal_candidate；downloadIterate() 下载；postsolveIterate() 调用 model::postsolve。

Review 推理：逐边界检查 owner、尺寸、驻留与同步，才能避免把 device candidate、Host copy 和 original solution 当成同一对象。

综合题 2：正常 cadence check 是否需要完整 candidate D2H？

展开参考答案

结论：不需要；正常路径在 Device 上计算 resident check，只下载一个 112-byte packet。仅不确定/fallback、证书或最终输出需要更大下载。

代码证据：checkPartialsKernel 与 checkPacketKernel 生成 CheckPacket，普通路径记录 ordinary_check_d2h_bytes；完整候选经 downloadIterate() 单独计入 candidate_downloads。

Review 推理：必须用 counters 和 Systems trace 核对每个 boundary 的实际 bytes；“API 能下载”不等于正常路径必须下载。

综合题 3：证明当 N > 65535 × 256 时 grid-stride kernel 仍覆盖每个索引。

展开参考答案

结论：满 grid 提供 stride 个起点 0..stride-1；任意 i < N 都可唯一写成 i = r + q × stride，由起点 r 的线程在第 q 次循环访问。

代码证据：stride = blockDim.x * gridDim.x，循环执行 index += stride；宽索引 GridIndex 与 static_assert 防止支持范围内的 stride 加法溢出。

Review 推理：覆盖证明还需确认 grid 含所有 residue 起点、循环条件是 index < size，且索引类型能表示 N 与后续加法。

综合题 4：如何检查 CUDA graph 捕获的 dependencies 是否可能过期？

展开参考答案

结论：每个参与 capture 的 problem/workspace/vector 提交其 lifetime token；command buffer 只保存 weak references，任何资源先销毁都会让 replay 明确失败。

代码证据：recordDependency(shared_ptr) 收集 token，endRecording() 移入 dependencies，replay() 在 cudaGraphLaunch 前执行 dependenciesAlive() 并返回 “dependency has expired”。

Review 推理：检查必须覆盖每种被捕获资源的 record call，并测试销毁任一资源后 replay 失败，而非只检查 graph handle 非空。

四遍 Review 模式

不要在一遍里同时追所有问题。每一遍只接受与本目标相关的证据，并把 reusable prompt 复制到 human/AI review 中。

Pass 1 · Interface and ownership

good signal

move-only handles、单一 owner、构造失败自动清理、明确的借用边界与 structured errors。

danger signal

裸 device pointer 越过 backend、隐式复制 handle、resource 比 graph/descriptor 更早销毁、失败后保留看似有效输出。

Human review prompt

“对每个跨函数对象标 owner、borrower、move、reset 和失败清理；指出任何无法唯一回答‘谁释放’的位置。”

AI review prompt

“只审接口与所有权。列出 handle/resource 生命周期、所有 move-only 约束、提前返回清理和错误传播；不要推断未展示的代码。”

Pass 2 · Numerical correctness

good signal

维度/alias/finite guards、明确 reduction 顺序、容差有尺度、Host oracle、postsolve 后原模型 KKT。

danger signal

NaN 比较默认通过、只验证 transformed model、改变运算顺序却复用旧 tolerance、性能样本未核对迭代轨迹。

Human review prompt

“从输入尺度到最终 KKT 追踪每次浮点变换、reduction 与容差；为 NaN/Inf、零尺度和边界值写反例。”

AI review prompt

“只审数值正确性。区分 bitwise determinism、稳定性与 tolerance acceptance；用源码证据指出 oracle 是否独立。”

Pass 3 · Concurrency and CUDA semantics

good signal

producer/consumer 同 stream、有目的的同步、async error 明确汇合、capture 内外边界清楚、replay 前验证依赖。

danger signal

Host 在同步前读取 D2H、library handle 绑定不同 stream、launch success 被当执行 success、graph 捕获悬空地址。

Human review prompt

“画出 stream timeline，标每个 enqueue、数据依赖、event/sync、Host read 与错误观察点；寻找跨 stream 无 happens-before 的边。”

AI review prompt

“只审并发与 CUDA 语义。逐项证明顺序、可见性、同步和 graph resource lifetime；无法证明时标为待运行验证。”

Pass 4 · Performance

good signal

先用阶段 counters 定位，再用 Systems/Compute；同模型同选项比较；同时报告每步成本、迭代数和 correctness gate。

danger signal

用 launch 数替代 wall time、从三个样本外推全部模型、只看成功子集、把 sanitizer clean 当成 speedup 证据。

Human review prompt

“写出瓶颈假设、可证伪指标、控制变量、正确性护栏和停止条件；先问优化是否命中端到端主导项。”

AI review prompt

“只审性能证据。区分已实现、已测量和待测假设；拒绝缺少 baseline、样本范围、迭代轨迹或 KKT 接受的加速结论。”

术语表

CSR
Compressed Sparse Row；用 row offsets、column indices 和 values 表示稀疏矩阵。
SpMV
Sparse matrix-vector multiply；HiPDLP 每个生产 step 执行 forward 与 transpose 两次。
primal
原问题变量及其候选、anchor、reflection 等迭代向量。
dual
约束侧变量；与 primal 一起定义残差、目标和 KKT 条件。
reflection
围绕当前 candidate 的反射点；Halpern PDHG 下一次 SpMV 的输入之一。
Halpern anchor
Halpern 迭代固定或重启后的参考点，与 reflection 按权重混合。
resident
数据保持在当前 backend；resident check 在 Device 上计算指标而不先下载完整向量。
H2D
Host-to-Device transfer；模型、向量或 scalar parameter 的上传。
D2H
Device-to-Host transfer；check packet、error flag 或完整 candidate 的下载。
pinned memory
页锁定 Host memory；用于可复用、可异步的 CUDA transfer staging。
stream
有序的 CUDA 工作队列；同一 stream 中的操作保留提交顺序。
event
记录 Device timeline 的 CUDA 对象；适合 GPU 阶段计时和顺序标记。
warp
一起调度的一组 CUDA threads；分支路径不同时可能序列化。
occupancy
活跃 warps 相对硬件上限的比例；是延迟隐藏线索，不是性能结论。
coalescing
相邻 threads 的 memory access 合并为较少 transaction 的访问性质。
divergence
同一 warp 的 threads 选择不同分支，导致路径分批执行。
graph capture
把 stream 中提交的固定设备操作记录成 CUDA Graph，以 executable 重放。
deterministic reduction
固定 partial grouping 与合并树；其保证必须限定到具体 kernel 和环境。
host oracle
当紧凑 Device check 不足以裁决时，在 Host 上用完整数据重新计算的参考路径。
postsolve
撤销 scaling/transform，把求解空间 candidate 恢复成原模型 HighsSolution。
KKT
Karush-Kuhn-Tucker 条件；最终在原模型上检查 primal/dual feasibility 与 gap。
command buffer
HiPDLP 对可 replay 后端工作的抽象；CUDA 实现由 graph executable 支撑。
structured error
带 ErrorCode 与消息的失败值；不得伪装成成功状态或静默 fallback。
