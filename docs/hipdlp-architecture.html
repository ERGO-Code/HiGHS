CUDA graph 的弱生命周期依赖

shared lifetime token weak dependency

每个 CUDA problem/vector/workspace resource owns 一个 shared lifetime token。录制期间，操作把 token 记入依赖集；完成录制时，CommandBufferHandle 保存的是 weak_ptr，因此 graph 不拥有被捕获的数据。

replay 前逐项检查弱依赖；任一资源句柄已经析构，就返回 “command buffer dependency has expired”，而不是访问悬空 Device 地址。

实现： recordDependency / replay

驻留结论

CPU：Problem、16 个向量与两个 workspace scratch 都在 Host；句柄调用不跨总线。

CUDA：这些求解数据常驻 Device；Host 保留 Problem::Data、OriginalModel、HostIterate 与最终 HighsSolution。边界检查优先只下载 compact packet，需要 Host oracle / postsolve 时才下载候选向量。

Setup H2D · Host → Device

bindProblem 上传 costs、bounds、row types、matrix 与 transpose；prepareCheckWorkspace 另上传 scaling、原模型 certificate 与 check 数据。它们在迭代前建立常驻 Device 副本。

Candidate D2H · Device → Host

Production step：五个有序操作

入口及四次 Backend 调用保持源码顺序。橙色卡片标出恰好两次 SpMV；A * next_primal 不在每个生产步中，它只在边界准备 candidate products 时发生。

  1. enqueueHalpernPdhgStep

    Host 控制器校验 14 个句柄、正步长、迭代计数与 scalar offset，并构造 primal step、dual step、anchor weight。

    CPU lane 同步调用 serial Backend；任一 api::Error 立即返回。
    CUDA lane 向 Backend stream 排队；录制时同样的调用成为 CUDA graph 节点。

  2. fusedProjectedPrimalUpdateAndReflect

    从 current_primal 与 current_aty 计算投影后的 primal_candidate，并产生 reflected_primal = 2*candidate-current。

    CPU lane · column loop serial for col：梯度更新、lower/upper clamp、反射与 finite check。
    CUDA lane · custom kernel projectedPrimalKernel<true>，column-sized grid-stride launch。

  3. multiplyAndProjectedDualUpdateAndReflect

    组合操作先计算 A * reflected_primal → reflected_ax，随后以 row bounds 更新、投影并反射 dual；forward product 不是一个额外的顶层算法调用。

    CPU lane · sparse loop + row loop multiplySparse(matrix, reflected_primal)，再执行 projected dual / reflection loop。
    CUDA lane · vendor + custom executeSpmv → cusparseSpMV，然后 projectedDualKernel<true>。
    SpMV 1/2 · A * reflected_primal

  4. fusedVectorBlend

    用 1/(next_iteration+1) 同时混合 primal/dual anchor 与 reflected vectors，写入 next_primal、next_dual。

    CPU lane · two serial loops 分别遍历 columns 与 rows，检查 weight 和输出有限性。
    CUDA lane · paired kernel 单次 vectorPairBlendKernel 覆盖 max(rows, cols)。

  5. multiplyTranspose，然后 commit state

    计算 A^T * next_dual → current_aty；成功后 swap current/next 指针并增加 iteration。这里没有 A * next_primal。

    CPU lane · transpose sparse loop multiplySparse(transpose, next_dual)；Host 完成 pointer swaps。
    CUDA lane · vendor SpMV executeSpmv → cusparseSpMV；排队成功后 Host 完成 pointer swaps。
    SpMV 2/2 · A^T * next_dual

顺序证据： algorithm/halpern_pdhg_step.cc · backend/cpu/cpu_backend.cc · backend/cuda/cuda_backend.cu

CUDA graph：1 direct + 39 recorded steps

在 40-step cadence 中，RecordedIterationBlock 捕获 39 个 production steps。每步 3 个 scalars，共 39 × 3 = 117 doubles = 936 bytes；replay 前上传参数，随后调用 cudaGraphLaunch。

Replay scheduling：The initial step and the first post-restart step execute directly. Short tails with fewer than 39 remaining steps execute directly.

Time-limit granularity：Host checks the time limit before submitting replay and after it completes; a submitted 39-step block cannot be interrupted by host time-limit checks.

Graph 保留资源的 weak lifetime dependencies，而不是拥有 problem/vector/workspace。捕获、实例化或 replay 的失败保持为 api::Error。

CUDA resident certificate screen eligibility gate

只有全部条件同时满足才启动 certificate kernels：

  • 编译环境：__aarch64__、__GLIBC__ == 2、__GLIBC_MINOR__ == 39、!defined(__FAST_MATH__)、FLT_RADIX == 2、DBL_MANT_DIG == 53、DBL_MAX_EXP == 1024、LDBL_MANT_DIG >= 53、LDBL_MAX_EXP >= DBL_MAX_EXP、FLT_EVAL_METHOD == 0。
  • 运行环境：gnu_get_libc_version() == "2.39"、fegetround() == FE_TONEAREST，且 AArch64 FPCR 的 ((3 << 22) | (1 << 24) | 3) mask 全为 0。
  • 维度：原 certificate problem 必须满足 num_rows + num_cols < 4503599627370496（严格小于 252）。check workspace 准备还会显式校验原模型 dimensions、bounds、cost、matrix 与 row map；这些失败返回 Error，不是 screen skip。

不满足 gate：跳过 recovery/norm/normalize/conditions/flags launches，certificate_screen_valid = false；默认保持 primal_ray_possible = true、farkas_possible = true，所以 certificate_possible = true。算法在 cadence certificate 分支下载或复用 full candidate，并调用 detectCertificate()；独立 Host verifier 是裁决者，resident screen 不会错误排除候选。

fallback 差异：启用了 stopping tolerance 且 rounding environment 不受支持时，requires_host_oracle = true，触发 full candidate D2H 和 raw convergence Host oracle；后续 certificate 分支复用该 candidate。仅因 252 维度 gate 失败不会单独设置 raw-oracle flag，但仍会因两个 possible flags 为 true 进入 full-candidate Host certificate verification。

查看 cuda_kernels.cu

问题 1：一个线程如何覆盖不止一个 column？

展开参考答案

结论：每个线程处理一个起始索引，并按整个 grid 的 stride 继续前进。

代码证据：index += blockDim.x * gridDim.x。

静态边界：源码能证明线程起点和 stride 递增关系，但前提是索引与下一次加法都可表示；它不能证明实际吞吐或 occupancy。

运行时工具：用大于一个满 grid 的 sentinel 向量做 CPU/CUDA 对照，再用 Nsight Compute 检查 achieved occupancy 与 memory throughput。

Review 推理：静态代码能证明覆盖方式；实际吞吐和 occupancy 仍需 profiler。

问题 2：blocks 上限 65535 是否把可处理的向量长度也限制为 65535 × 256？

展开参考答案

结论：不会；上限只限制并发起点数量，grid-stride loop 继续覆盖更大的 N。

代码证据：blockCount() cap blocks，但 kernel 的 for (...; index < size; index += stride) 不 cap size。

静态边界：循环形状能证明 block cap 不等于 size cap，但只有显式检查索引宽度与 index + stride 后才能把证明扩展到声明的最大尺寸。

运行时工具：以 N = 65535 × 256 + 1 的边界样例对照 CPU 输出，并在 Compute Sanitizer 下检查越界访问。

Review 推理：要同时审查循环和索引类型；只看 launch geometry 会错误地推断覆盖缺口。

问题 3：projection 分支和 atomicExch(error_flag, 1) 分别影响什么？

展开参考答案

结论：上下界 clamp 可能造成 warp divergence；atomic 只把 non-finite 失败汇总为单向错误标志。

代码证据：if (value < lower[index])、if (value > upper[index]) 与 recordNonFinite()。

静态边界：分支条件和只写 1 的幂等 error flag 可由源码验证；源码不能量化真实 bound 分布造成的 warp divergence。

运行时工具：注入 finite/non-finite 与不同 bound 分布的样例，用 Compute Sanitizer 验证错误路径，并用 Nsight Compute 查看 branch efficiency。

Review 推理：正确性可由分支和幂等标志判断；分支代价必须结合 bound 分布和 profiler 观察。

Checklist：

  • 为每个 kernel 写出 global index、stride 与边界条件。
  • 确认索引乘法不会在最大支持维度溢出。
  • 区分覆盖正确性、分支正确性与 occupancy 证据。

查看 cuda_backend.cu

问题 1：VectorHandle 为什么不暴露 double*？

展开参考答案

结论：opaque handle 把驻留位置和资源类型封装在 backend 内，阻止算法层直接解引用或跨 backend 混用。

代码证据：Handle<Tag> 私有持有 std::unique_ptr<Resource>，只有 CPU/CUDA backend 是 friend。

静态边界：C++ 类型系统能证明 opaque handle 的 copy/access 边界，不能证明运行时传入的 handle 属于同一 backend、尺寸匹配或尚未 move。

运行时工具：用 backend contract tests 覆盖跨 backend、moved-from、错误尺寸和 alias 输入，并在 CUDA 路径配合 Compute Sanitizer。

Review 推理：类型封装能证明访问边界；owner、尺寸与 alias 仍必须由具体 backend 在每次操作中校验。

问题 2：为什么小型 check packet 仍使用 pinned memory？

展开参考答案

结论：pinned Host buffer 支持可靠的异步 D2H staging，并可在多次 cadence boundary 复用。

代码证据：PinnedCheckPacket::allocate() 调用 cudaMallocHost(..., sizeof(CheckPacket))。

静态边界：cudaMallocHost 与复用路径能证明 buffer 类型和生命周期，不能证明传输重叠、固定 pinning 成本或端到端收益。

运行时工具：用 Nsight Systems 对齐 cadence boundary、D2H memcpy 和 stream synchronize，比较 pinned allocation 与复用成本。

Review 推理：复用和异步语义由代码可见；pinning 是否值得其固定成本需用边界频率与 timeline 衡量。

问题 3：连续 vector access 与 CSR SpMV 的访存证据为何不能混为一谈？

展开参考答案

结论：vector kernel 可按连续 index 获得 coalescing，而 CSR 的 index/value 访问受矩阵结构和 vendor kernel 控制。

代码证据：custom kernel 直接访问 current[index]；SpMV 通过 CSR descriptor 进入 cusparseSpMV。

静态边界：源码只证明 custom vector 的显式下标和 cuSPARSE descriptor 边界，不能推出 vendor kernel 的 cache、transaction 或合并访问行为。

运行时工具：用 Nsight Compute 的 Memory Workload Analysis 分别观察 custom kernel 与 cuSPARSE kernel，并按矩阵结构分桶比较。

Review 推理：源码可分类访问模式，但 cache hit、transaction 和有效带宽必须由 Nsight Compute 证明。

Checklist：

  • 标出每个数组的 owner、驻留位置、尺寸与释放点。
  • 为每次 H2D/D2H 写明目的、字节数与同步点。
  • 区分 device memory、static shared、dynamic shared 与 pinned Host memory。

→
One streamkernel → SpMV → kernel
→

≠

HiPDLP 例子：Backend 的 custom kernels、cuBLAS 与 cuSPARSE 都绑定到同一 stream；生产 step 依赖 stream 顺序，不在每个 kernel 后同步，boundary 才下载 packet/error 并等待。

CUDA event timing：beginTiming() 用 cudaEventRecord 在 backend stream 记录 start；endTiming() 记录 stop，调用 cudaEventSynchronize，再用 cudaEventElapsedTime 得到两个事件之间的 GPU elapsed time。它衡量该 stream 上事件之间的 Device 工作，不等同于整个 Host 调用耗时。

对比 Host timing：围绕 cudaStreamSynchronize 观察到的 Host synchronization wall time 还包含此前排队工作的等待、D2H 完成、runtime/driver 开销与 Host 被阻塞的时间。分析慢点时必须说明测量边界，不能拿 event seconds 直接替代端到端 wall time。

查看 stream 与 handle 绑定

问题 1：没有逐 kernel 同步，第二次 SpMV 如何等待前一个 kernel？

展开参考答案

结论：同一 CUDA stream 内的操作按提交顺序执行，因此数据依赖不需要 Host 逐项等待。

代码证据：custom launches 使用 impl_->stream.get()，cuBLAS/cuSPARSE handles 也由 *SetStream 绑定它。

静态边界：handle 绑定与调用点能证明预期使用同一 stream，不能证明运行时没有漏绑 handle、默认 stream 工作或外部并发。

运行时工具：用 Nsight Systems 的 stream timeline 核对 producer/consumer 顺序，并以 Compute Sanitizer racecheck 检查并发 hazard。

Review 推理：要证明顺序，必须追踪所有 producer/consumer 是否真的在同一 stream；仅看到异步 API 名称不够。

问题 2：异步 kernel 的 non-finite 错误何时变成 Host 上的 api::Error？

展开参考答案

结论：kernel 先写 device error_flag，Host 在显式检查边界异步复制该 flag 并同步 stream 后形成 structured error。

代码证据：synchronizeAndCheck() 执行 cudaMemcpyAsync、cudaStreamSynchronize，再检查 host_error。

静态边界：控制流能证明 device flag 经 D2H 和 synchronize 转成 api::Error，不能证明每种异步失败都写入该 flag。

运行时工具：注入 NaN 和非法访问样例，结合错误传播测试与 Compute Sanitizer 验证同步边界实际暴露失败。

Review 推理：launch status 只覆盖提交错误；异步执行错误必须在同步或后续 API 边界显式暴露。

问题 3：D2H 已 enqueue 后，Host 能否立刻读取目标 buffer？

展开参考答案

结论：不能；必须等待该 stream 完成复制，之后 Host 读取才有定义且可见。

代码证据：download path 在 cudaMemcpyAsync(..., cudaMemcpyDeviceToHost, stream) 后调用 cudaStreamSynchronize(stream) 再 publish。

静态边界：语句顺序能证明当前路径在 synchronize 后 publish，不能证明所有调用路径都遵守同一可见性边界或传输何时完成。

运行时工具：用 sentinel integration test 检查 Host 读取值，并在 Nsight Systems 中确认 memcpy 完成先于 Host consumer。

Review 推理：pinned memory 允许异步传输但不取消完成依赖；检查读取位置是否在同步之后。

Checklist：

  • 为每个 producer/consumer 标出 stream 与提交顺序。
  • 区分 enqueue 成功、device 执行成功和 Host 可见完成。
  • 把每个 synchronize 关联到明确的正确性或计时目的。

问题 1：看到 kernel 很短，先用 Nsight Systems 还是 Nsight Compute？

展开参考答案

结论：先用 Systems 判断时间是否来自 launch gaps、同步或某个 kernel，再对主导 kernel 使用 Compute。

代码证据：SolveDiagnostics 已分出 setup、step、boundary、download 与 replay counters，可先限定阶段。

静态边界：诊断字段能划分代码阶段，却不能把 wall time 归因到 launch gap、同步、copy 或特定 kernel。

运行时工具：先用 Nsight Systems 定位主导时间段，再只对主导 kernel 运行 Nsight Compute。

Review 推理：Compute 的深度指标不能回答端到端调度占比；先定位再下钻可避免优化非瓶颈。

问题 2：低 occupancy 是否足以证明 kernel 是瓶颈？

展开参考答案

结论：不足；低 occupancy 可能仍隐藏了足够延迟，也可能该 kernel 根本不占主要 wall time。

代码证据：checkPartialsKernel 使用 __shared__ CheckPartial shared[256]，但只在 cadence boundary 运行。

静态边界：static shared 声明能给出潜在资源约束，不能证明 achieved occupancy、stall 原因或该 kernel 的 wall-time 权重。

运行时工具：联合 Nsight Compute 的 occupancy/stall/bandwidth 指标与 Nsight Systems 的 duration、频率和端到端占比。

Review 推理：必须联合 kernel duration、调用频率、带宽、stall 与端到端占比，单一指标只是线索。

问题 3：融合两次 vector launch 时，什么证据能防止“更少 launch = 更快”的误判？

展开参考答案

结论：同时比较 launch gaps、kernel duration、有效线程比例、每步成本和总迭代数。

代码证据：vectorPairBlendKernel 按 max(num_cols, num_rows) launch，并对 row/column 分别作 size guard。

静态边界：launch geometry 能显示融合减少节点并可能产生 idle lanes，不能证明 register pressure、调度成本或净 speedup。

运行时工具：以相同模型、状态、残差和 KKT 结果做 A/B，使用 Systems 比较 gaps、Compute 比较 active threads 与 registers。

Review 推理：融合减少固定成本却可能增加空转或寄存器压力；只有同工作量、同正确性轨迹的测量可裁决。

Checklist：

  • 先分离 setup、steady state、boundary 与最终验证。
  • 同时报告每步成本、调用次数、迭代数和接受状态。
  • 把 occupancy、coalescing、divergence 与实际 wall-time 占比配对。

问题 1：为什么 scratch buffer 应在 bind/setup 阶段创建，而不是每次 SpMV 创建？

展开参考答案

结论：workspace 尺寸由 descriptor 和算法决定，可按 matrix/transpose 最大值一次分配并在所有 step 复用。

代码证据：querySpmvBufferSize() 填写两份 spmv_buffer_size，随后只分配一个最大尺寸的 spmv_buffer。

静态边界：setup 路径能证明 HiPDLP 只分配一个最大 scratch buffer，不能证明 vendor 内部无额外分配或 descriptor 永不失配。

运行时工具：用 Nsight Systems 的 CUDA API trace 检查 steady state 无 allocation，并以不同 matrix/transpose 尺寸重复 SpMV contract tests。

Review 推理：这能消除迭代内 allocation；仍需确认 descriptor 生命周期和尺寸变化不会让复用失效。

问题 2：零 NNZ 时为什么不直接调用 cuSPARSE？

展开参考答案

结论：结果已知为零，专用 fill kernel 避免依赖空 CSR 的 vendor 行为并保持输出定义明确。

代码证据：executeSpmv 在 matrix.num_nonzeros == 0 时调用 launchFill(..., 0.0, output)。

静态边界：零 NNZ 分支能证明 CUDA 输出被显式写零，不能单独证明 CPU/CUDA 契约一致或后续检查覆盖完整。

运行时工具：用零行、零列和零 NNZ 模型做 CPU/CUDA differential test，并在 Compute Sanitizer 下验证 fill 边界。

Review 推理：边界分支应与 CPU 语义一致，并仍经过后续需要的 finite/error 检查。

问题 3：源码中的 CUSPARSE_SPMV_ALG_DEFAULT 能否证明具体 grid 或性能？

展开参考答案

结论：不能；HiPDLP 只选择 API、descriptor 与算法枚举，内部 kernel geometry 由 library/runtime 决定。

代码证据：调用点是 cusparseSpMV(..., CUSPARSE_SPMV_ALG_DEFAULT, spmv_buffer)，没有 HiPDLP launch dimensions。

静态边界：wrapper 只能证明 descriptor、枚举与 API 参数，不能证明 vendor 选择的 kernel geometry、scratch traffic 或性能。

运行时工具：用 Nsight Systems 识别实际 cuSPARSE kernels，再用 Nsight Compute 按矩阵 shape/nnz 分析它们。

Review 推理：实际 kernel、scratch traffic 和矩阵结构影响必须由 Systems/Compute trace 观察，不能从 wrapper 推断。

Checklist：

  • 验证 CSR dimensions、index width、descriptor 和 dense vector 尺寸一致。
  • 确认 scratch 查询、分配与复用生命周期覆盖 matrix 和 transpose。
  • 把 library status 转成 structured error，并单独验证零 NNZ。

问题 1：Graph 捕获的是算法决策还是已排入 stream 的设备操作？

结论：捕获的是 recording 区间内提交到 stream 的 kernels/library calls；Host 的停止、时间与 restart 决策留在 graph 外。

代码证据：cudaStreamBeginCapture/cudaStreamEndCapture 包住 repeated enqueueHalpernPdhgStep，boundary check 另行执行。

问题 2：为什么是 39-step replay，而不是完整 40-step block？

展开参考答案

结论：第 40 步后需要 Host 控制的 cadence boundary；录 39 步保持初始/重启后的 direct step 和 boundary 对齐。

代码证据：kConvergenceCadence == 40、kRecordedStepCount == 39，replay 条件要求 total_iterations % 40 == 1。

静态边界：常量和 modulo 条件能证明预期 1 + 39 调度，不能穷尽 restart、limit 与 short-tail 的动态组合。

运行时工具：用 1/39/40/41-step、restart 和 limit integration cases 检查 counters，并在 Systems timeline 核对 direct/replay 边界。

Review 推理：检查 off-by-one 必须同时模拟初始、restart、iteration limit 与 short tail，而不能只看常态循环。

问题 3：Graph executable 存在时，为什么仍要检查依赖生命周期？

展开参考答案

结论：graph nodes 捕获了资源地址；若 problem/workspace/vector 已释放，executable 仍非空但其指针已失效。

代码证据：CudaCommandBufferResource 保存 std::weak_ptr<int> dependencies，replay() 先调用 dependenciesAlive()。

静态边界：weak_ptr guard 能证明已登记 token 的过期检测，不能证明 capture 使用的每个资源都调用了 recordDependency。

运行时工具：逐类销毁 problem/workspace/vector 后尝试 replay，断言 structured error，并用 Compute Sanitizer 排除漏登记导致的 use-after-free。

Review 推理：Graph object 的生命周期不等于被捕获资源的生命周期；重放前的显式 guard 防止 use-after-free。

Checklist：

  • 证明参数地址、vector、workspace、problem 在每次 replay 时仍有效。
  • 覆盖 capture、instantiate、launch、async execution 和 cleanup 失败。

问题 1：atomicExch(error_flag, 1) 会不会引入 reduction 顺序的不确定性？

展开参考答案

代码证据：recordNonFinite() 仅执行 atomicExch(error_flag, 1)，数值 partials 在独立的 shared-memory tree 中合并。

问题 2：固定 reduction tree 是否足以保证所有 GPU、编译器与 library 版本 bitwise 相同？

展开参考答案

结论：不足；它固定自有 kernel 的合并拓扑，但不能控制 cuSPARSE 内部顺序、编译选项或硬件差异。

代码证据：custom check 使用 for (distance = 128; ...)，而 SpMV 使用 vendor-controlled CUSPARSE_SPMV_ALG_DEFAULT。

静态边界：固定 tree 只约束自有 reduction 源码；cuSPARSE、编译 flags、driver 与 GPU 架构仍在证明边界外。

运行时工具：跨 GPU、toolchain 与 library 版本重复运行，分别比较 bit pattern、残差轨迹和最终 KKT 接受结果。

Review 推理：确定性声明必须限定组件、平台与容差；跨环境要靠重复运行和数值接受测试验证。

问题 3：为什么 resident check 通过后仍需要 postsolve 和原模型 KKT？

展开参考答案

结论：resident check 针对变换/缩放空间与紧凑指标；最终用户结论必须在恢复后的原 HighsLp 上独立验证。

代码证据：solver 先调用 model::postsolve，再调用 verification::verifyKkt(original_model.lp(), solution, ...)。

静态边界：控制流能证明 postsolve 后调用独立 verifier，不能证明映射、下载值或 verifier 数值实现本身无缺陷。

运行时工具：用 CPU differential cases 和故障注入破坏 transformed candidate、download 或 mapping，确认 original-model KKT 会拒绝。

Review 推理：分层 oracle 能发现 transformation、download 或 backend 的共同错误，避免同源计算自证正确。

Checklist：

  • 标出每个 reduction 的顺序、类型、容差和 non-finite 路径。
  • 把 bitwise determinism、数值稳定性与接受容差分开陈述。
  • 保留 Host oracle、postsolve 与原模型 KKT 的独立性。

综合题 1：追踪 primal_candidate：从分配、kernel 写入、resident check、download 一直到 postsolve。

展开参考答案

结论：它是 backend-owned column vector：setup 创建，primal kernel 写入，边界检查在 Device 上读取，必要时下载到 HostIterate::primal，最后由 postsolve 恢复原模型语义。

代码证据：createIterationVectors() 创建它；fusedProjectedPrimalUpdateAndReflect(..., *state.primal_candidate, ...) 写入；check_input.primal = state.primal_candidate；downloadIterate() 下载；postsolveIterate() 调用 model::postsolve。

静态边界：调用链能证明 owner、handle 传递和 postsolve 顺序，不能证明运行时地址、内容与 stream 完成时刻。

运行时工具：用 cuda-gdb 或受控 sentinel instrumentation 观察 candidate，再以 Nsight Systems 核对 resident check、D2H 和 Host consumer 顺序。

Review 推理：逐边界检查 owner、尺寸、驻留与同步，才能避免把 device candidate、Host copy 和 original solution 当成同一对象。

综合题 2：正常 cadence check 是否总是只需 112-byte packet？

展开参考答案

结论：不是。resident check 的 baseline 只下载 112-byte packet；requires_host_oracle 会为 raw metrics 下载完整候选，而 certificate_possible 在普通 cadence 也可能触发完整 candidate D2H，随后进入 detectCertificate()，不是 raw convergence host oracle。terminal/postsolve 路径也会按需下载或复用同一候选。

代码证据：checkPartialsKernel 与 checkPacketKernel 生成 CheckPacket；solver 分别在 check.requires_host_oracle 和后续 certificate_possible 分支调用缓存的 download_candidate()，后者再调用 detectCertificate()；完整候选统一计入 candidate_downloads。

静态边界：控制流能证明 packet baseline 以及 host-oracle、certificate、terminal/verification 的 full-candidate 触发器，不能证明运行时触发频率和实际 bytes。

运行时工具：联合 candidate_downloads、host_oracle_checks、certificate_checks 与 Nsight Systems D2H trace 区分每种触发器。

Review 推理：必须用 counters 和 Systems trace 核对每个 boundary 的实际 bytes；“API 能下载”不等于正常路径必须下载。

综合题 3：对显式使用 GridIndex 的 differenceKernel 和 vectorPairBlendKernel，证明当 N > 65535 × 256 时仍覆盖每个索引。

展开参考答案

结论：满 grid 提供 stride 个起点 0..stride-1；任意 i < N 都可唯一写成 i = r + q × stride，由起点 r 的线程在第 q 次循环访问。该证明只覆盖显式使用 GridIndex 的 kernels。

代码证据：differenceKernel 和 vectorPairBlendKernel 以 GridIndex 计算 stride 与 index += stride；static_assert 保证最大支持 HighsInt 索引再加最大 grid stride 仍能由 GridIndex 表示。projectedPrimalKernel 等仍用 HighsInt，所以这条无溢出证明不能外推到所有 grid-stride loops。

静态边界：GridIndex 与 static_assert 的无溢出证明只适用于显式使用该类型的 kernels；仍以 HighsInt 递增的 loops 必须单独审计。

运行时工具：用 N = 65535 × 256 + 1 的 sentinel 对照和 Compute Sanitizer 验证边界执行；该样例不能替代最大 HighsInt 的静态证明。

Review 推理：覆盖证明还需确认 grid 含所有 residue 起点、循环条件是 index < size，且索引类型能表示 N 与后续加法。

综合题 4：如何检查 CUDA graph 捕获的 dependencies 是否可能过期？

展开参考答案

结论：每个参与 capture 的 problem/workspace/vector 提交其 lifetime token；command buffer 只保存 weak references，任何资源先销毁都会让 replay 明确失败。

代码证据：recordDependency(shared_ptr) 收集 token，endRecording() 移入 dependencies，replay() 在 cudaGraphLaunch 前执行 dependenciesAlive() 并返回 “dependency has expired”。

静态边界：weak dependency set 与 replay guard 只能覆盖已登记资源，不能证明 capture 期间的每个 device pointer 都有对应 token。

运行时工具：为 problem、workspace 和每类 vector 做逐一销毁/重放测试，并在 Compute Sanitizer 下确认没有 guard 前 use-after-free。

Review 推理：检查必须覆盖每种被捕获资源的 record call，并测试销毁任一资源后 replay 失败，而非只检查 graph handle 非空。

四遍 Review 模式

不要在一遍里同时追所有问题。每一遍只接受与本目标相关的证据，并把 reusable prompt 复制到 human/AI review 中。

Pass 1 · Interface and ownership

good signal

move-only handles、单一 owner、构造失败自动清理、明确的借用边界与 structured errors。

danger signal

裸 device pointer 越过 backend、隐式复制 handle、resource 比 graph/descriptor 更早销毁、失败后保留看似有效输出。

Human review prompt

“对每个跨函数对象标 owner、borrower、move、reset 和失败清理；指出任何无法唯一回答‘谁释放’的位置。”

AI review prompt

“只审接口与所有权。列出 handle/resource 生命周期、所有 move-only 约束、提前返回清理和错误传播；不要推断未展示的代码。”

Pass 2 · Numerical correctness

good signal

维度/alias/finite guards、明确 reduction 顺序、容差有尺度、Host oracle、postsolve 后原模型 KKT。

danger signal

NaN 比较默认通过、只验证 transformed model、改变运算顺序却复用旧 tolerance、性能样本未核对迭代轨迹。

Human review prompt

“从输入尺度到最终 KKT 追踪每次浮点变换、reduction 与容差；为 NaN/Inf、零尺度和边界值写反例。”

AI review prompt

“只审数值正确性。区分 bitwise determinism、稳定性与 tolerance acceptance；用源码证据指出 oracle 是否独立。”

Pass 3 · Concurrency and CUDA semantics

good signal

producer/consumer 同 stream、有目的的同步、async error 明确汇合、capture 内外边界清楚、replay 前验证依赖。

danger signal

Host 在同步前读取 D2H、library handle 绑定不同 stream、launch success 被当执行 success、graph 捕获悬空地址。

Human review prompt

“画出 stream timeline，标每个 enqueue、数据依赖、event/sync、Host read 与错误观察点；寻找跨 stream 无 happens-before 的边。”

AI review prompt

“只审并发与 CUDA 语义。逐项证明顺序、可见性、同步和 graph resource lifetime；无法证明时标为待运行验证。”

Pass 4 · Performance

good signal

先用阶段 counters 定位，再用 Systems/Compute；同模型同选项比较；同时报告每步成本、迭代数和 correctness gate。

danger signal

用 launch 数替代 wall time、从三个样本外推全部模型、只看成功子集、把 sanitizer clean 当成 speedup 证据。

Human review prompt

“写出瓶颈假设、可证伪指标、控制变量、正确性护栏和停止条件；先问优化是否命中端到端主导项。”

AI review prompt

“只审性能证据。区分已实现、已测量和待测假设；拒绝缺少 baseline、样本范围、迭代轨迹或 KKT 接受的加速结论。”

术语表

CSR
Compressed Sparse Row；用 row offsets、column indices 和 values 表示稀疏矩阵。
SpMV
Sparse matrix-vector multiply；HiPDLP 每个生产 step 执行 forward 与 transpose 两次。
primal
原问题变量及其候选、anchor、reflection 等迭代向量。
dual
约束侧变量；与 primal 一起定义残差、目标和 KKT 条件。
reflection
围绕当前 candidate 的反射点；Halpern PDHG 下一次 SpMV 的输入之一。
Halpern anchor
Halpern 迭代固定或重启后的参考点，与 reflection 按权重混合。
resident
数据保持在当前 backend；resident check 在 Device 上计算指标而不先下载完整向量。
H2D
Host-to-Device transfer；模型、向量或 scalar parameter 的上传。
D2H
Device-to-Host transfer；check packet、error flag 或完整 candidate 的下载。
pinned memory
页锁定 Host memory；用于可复用、可异步的 CUDA transfer staging。
stream
有序的 CUDA 工作队列；同一 stream 中的操作保留提交顺序。
event
记录 Device timeline 的 CUDA 对象；适合 GPU 阶段计时和顺序标记。
warp
一起调度的一组 CUDA threads；分支路径不同时可能序列化。
occupancy
活跃 warps 相对硬件上限的比例；是延迟隐藏线索，不是性能结论。
coalescing
相邻 threads 的 memory access 合并为较少 transaction 的访问性质。
divergence
同一 warp 的 threads 选择不同分支，导致路径分批执行。
graph capture
把 stream 中提交的固定设备操作记录成 CUDA Graph，以 executable 重放。
deterministic reduction
固定 partial grouping 与合并树；其保证必须限定到具体 kernel 和环境。
host oracle
当紧凑 Device check 不足以裁决时，在 Host 上用完整数据重新计算的参考路径。
postsolve
撤销 scaling/transform，把求解空间 candidate 恢复成原模型 HighsSolution。
KKT
Karush-Kuhn-Tucker 条件；最终在原模型上检查 primal/dual feasibility 与 gap。
command buffer
HiPDLP 对可 replay 后端工作的抽象；CUDA 实现由 graph executable 支撑。
structured error
带 ErrorCode 与消息的失败值；不得伪装成成功状态或静默 fallback。
